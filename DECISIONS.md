# Technical decisions

## Single HTML, no runtime packages

Bun bundles strict TypeScript into one browser IIFE. The build inserts the bundle and CSS into an HTML shell, calculates the script’s SHA-256 CSP hash and writes `dist/fieldboard.html`. No modules, workers, fonts, images or sidecar files are loaded at runtime. There are no bundled third-party runtime licences because the application uses only its own code and browser APIs.

A framework was not needed for this board. DOM nodes are reused by column/card identity so that moving one card does not replace a thousand-card board. Styling is embedded; symbols and system fonts replace icon/font downloads.

## One atomic workspace record

IndexedDB is the system of record. Each mutation writes the whole validated workspace in a strict-durability transaction. This makes the atomicity boundary include card order, completion state and activity together. A saved acknowledgment comes from `transaction.oncomplete`, never a successful request or an optimistic render.

The tradeoff is write amplification and a practical workspace-size limit. Append-only history and full-state localStorage drafts can exceed the smaller journal quota before IndexedDB fills. Quota failures stay visible. This MVP does not prune history or quietly stop journalling to hide that limit.

Schema version 2 adds completion timestamps to version-1 data. Migration runs in the IndexedDB upgrade transaction, preserving storage identity. Unknown future schemas are rejected instead of guessed at.

## Drafts and concurrent tabs

The localStorage journal is written before submitting a new workspace state. A later queued draft includes its in-flight predecessor so startup can distinguish a committed predecessor from an unrelated conflicting revision after a crash. Draft clearing is conditional on the previously observed journal value.

Web Locks provides an exclusive editor lock. A second tab cannot edit until the first closes. IndexedDB revision comparisons are an additional stale-writer check, not a claim of multi-user collaboration. localStorage comparisons alone are not cross-process compare-and-swap, which is why they are not the concurrency authority.

Raw text has a separate journal. Text is also retained in memory if that journal fails, and an independent error prevents unrelated successful writes from making the UI claim the rejected text was saved. The error offers a draft download. Storage denial cannot be made durable by software; closing the tab while both stores reject writes can lose unexported text.

## Activity and undo

Each card mutation records actor, action, timestamp and complete before/after values. Reordering also logs cards whose numeric positions change. Deleted cards retain history. Undo restores a previous session state but appends audit entries rather than rewinding history. Member records referenced by history remain available.

Restore is an explicit whole-workspace replacement with confirmation and a cleared undo stack. JSON preserves domain entities and history; the local revision advances independently to maintain concurrency safety.

## Local snapshots are not backups

A snapshot stores the committed workspace once per active local day. The last seven snapshot dates are retained. Launch and a one-minute timer provide catch-up while the app runs; there is no background claim while the file is closed. User-downloaded JSON is the recovery path for another profile, changed file identity or device loss.

## Markdown and browser security

Markdown is a deliberately small allowlist renderer, not a general HTML interpreter. Text is escaped before formatting. Only HTTP(S) Markdown links become anchors, with `noopener noreferrer`; images stay textual. A CSP permits only the build-hashed script, blocks resource images, connections, frames, objects and form submission, and permits embedded styles. Stored user links are navigation data, not runtime dependencies.

## Verification boundaries

Bun unit tests cover the domain, draft/revision logic, schema migration and snapshot retention. Playwright exercises the isolated built HTML with networking disabled, using separate persistent profiles for recovery tests. Crash testing kills the actual test-owned browser process while a strict transaction is held open.

The container runs as root, so these Chromium tests require the test harness’s sandbox exception. That is not normal desktop acceptance. The same suite also passes as an unprivileged desktop user with the sandbox enabled; a normal headed launch is still unrecorded. No sandbox-disabling instruction is given to end users. The unflagged Linux browser gate, physical 60 fps test and full visual review remain open. Supplemental tests first observed passing after implementation are documented as such rather than being described as red-first proof.

## Tier boundary

Tier 1 and the mandatory deployment/safety requirements retain their original acceptance limits. The explicit request to integrate the copied FPGA estimation methodology authorizes a bounded planning extension before those limits close; it does not authorize the rest of Tier 2/3. The MVP used one board per newly created project; a later release ("Boards, My work, templates and bulk actions" below) exposes the board management the data model already supported.

## IED planning extension

IED is separate from the original unitless card estimate. Optional schema-2 fields preserve old workspaces byte-for-byte on load and avoid assigning units to old data. Planning fields are structurally validated in live cards, calibration snapshots and historical before/after records. Unknown future schema versions remain rejected. Downgrading to an older app is not supported for newly added data; no compatibility guarantee is inferred from sharing a schema number.

The calculation module implements the reference formulas rather than copying the notes' rounded examples. Verification scales only verification. Debug and timing tasks use an unsplit range because the reference does not supply a split. Documentation is 10% of adjusted RTL by default; platform costs are added after module contingency. Independent ranges use conservative bounds. The architecture gate uses the maximum effective multiplier over those ranges, with 4 as the limit, and does not clamp the result.

All project cards count, including archived/done work. Unestimated cards are counted and withhold calendar quotes instead of becoming zero effort. Old unitless estimates are ignored. Whole-program bands are a separate sanity check, not another multiplier on the detailed sum. The integration band is additive and excluded from whole-program comparison.

Calendar output is a capacity scenario. Numbered sprint loads include module contingency; platform overheads remain visible as unallocated reserve. No scheduling, dependency or full sprint-lifecycle claim is made. Calibration observations copy their estimate inputs at recording time, so later edits cannot rewrite the measurement. The project summary uses the latest observation per task and never sums revisions or silently tunes factors.

The UI uses the existing journal, staging, undo and storage paths. Dynamic scope and learning text is escaped before rendering. The extension adds no runtime dependency or network access. Its Playwright assertions cover delivered-file interactions and persisted data; screenshots do not close faithful visual or motion acceptance.

## Theme and phone layout

`settings.theme` is an optional `"system" | "light" | "dark"` field, following the same additive-schema-2 discipline as the planning fields: absent on old and freshly created workspaces, validated structurally, and defaulting to System wherever it is missing. Every colour in `src/styles.css` is a CSS custom property on `:root`; the light values are the original, unchanged colours, so the light theme is a straight tokenisation, not a redesign.

Dark values are declared twice, byte-identical: once under `@media (prefers-color-scheme: dark)` scoped to `:root:not([data-theme="light"])` (System mode, or no override yet), and once under `:root[data-theme="dark"]` (an explicit override, regardless of the OS setting). There is no CSS preprocessor in this build, so duplication is the only way to express "follow the OS" and "force dark" as separate rules; `tests/theme-contrast.test.ts` parses both blocks out of the shipped CSS and asserts they are equal, so the two cannot drift silently.

The page has no theme JavaScript on first paint: before the workspace loads, `<html>` carries no `data-theme` attribute, so the `prefers-color-scheme` media query alone decides the rendered theme. `applyTheme()` only runs once the stored `settings.theme` is known, inside `render()`. This means a stored override that disagrees with the live OS theme can flash once, from the system theme to the override, the moment the workspace finishes loading; when the override agrees with the system theme there is nothing to change, so there is no flash. Making the first paint wait on IndexedDB to avoid that one case would cost every load a blank-page delay to save an edge case that already renders correctly, just a beat later.

`<meta name="color-scheme">` starts as `"light dark"` so native controls (date pickers, scrollbars) already follow the OS before any script runs, and `applyTheme()` keeps it in sync with the active theme afterward (`"light"`, `"dark"`, or `"light dark"` for System).

Buttons gained `appearance:none`. Without it, Chromium's native dark-mode button chrome painted a visibly lighter panel over the correct `background-color`, even though the computed style was already right — the deployed-file screenshots caught this, not a diff review. Resetting `appearance` is standard practice for a component that is already fully styled by the author and does not change anything a user can see in light mode.

WCAG AA contrast is checked for a deliberately chosen set of text/background pairs — the ones carrying actual status meaning (overdue, due soon, priority, done, error banner, planning warnings, label chips) plus the app's core text/surface combinations — not for every colour in the file. Several of the original light-mode colours (the eyebrow label, keyboard-hint text, empty-column placeholder, footer) were already below 4.5:1 before this work and are left as they were, since redesigning them would violate "keep the existing visual identity in light mode."

The phone-width layout needed only two changes: the card detail view's column selector is now visibly labelled "Move to…" instead of "Column" (its `aria-label` is unchanged, so no existing test needed to change), and `button{appearance:none}` above. The sidebar-collapse, board horizontal scroll and no-page-scroll behaviour already existed in `@media (max-width:700px)` before this release; `tests/phone-browser.test.ts` is new coverage of already-correct behaviour, not a layout rewrite.

## Flow control: WIP limits, blocked state, dependencies and epics

A column's `wipLimit` was already part of the schema-2 `Column` type and already validated structurally; this release only adds the positivity rule (a stored or written limit must be a positive integer, never zero or negative) and lets `updateColumn` write it. The header badge counts non-archived cards in the column, not the currently filtered/searched set — a WIP limit describes the column's real load, and a search filter narrowing the visible cards shouldn't make a loaded column look empty. The unlimited case keeps its previous behaviour (the filtered count) unchanged, so this is a narrowly scoped addition, not a redefinition of what the header already showed.

`blocked`, `blockedBy` and `parentId` are optional additive schema-2 card fields, following the same discipline as `milestoneId`: absent on old and freshly created cards, validated structurally in `checkCard` (shape only, so Activity history validates it without needing the project graph), and validated relationally — self-reference, duplicates, cross-project references, cycles — only against live cards in `validateWorkspace`. A later deletion or re-parenting can therefore not strand old history the way a relational re-check would. `setBlocked` is the one dedicated mutation helper this release adds (beyond plain `editCard` patches used for `blockedBy`/`parentId`), because blocking carries real business logic — a required, trimmed reason, and a `since` timestamp that is set once and preserved across reason edits — that belongs in the model, not duplicated in the UI.

Cycle detection for both relations runs as a full-graph DFS inside `validateWorkspace` (coloured white/grey/black, `fail()` on a grey revisit) rather than inside the mutation functions themselves: because `Session.change` already calls `validateWorkspace` after every mutation (see "One atomic workspace record"), any cycle introduced by `editCard(...,{blockedBy:...})` or `{parentId:...}` is caught at commit time without a second, separate relational-check code path to keep in sync with the first. `blockedBy` cycles are checked over the general edge set (`c => c.blockedBy ?? []`); `parentId` cycles reuse the same checker with a single-edge view (`c => c.parentId ? [c.parentId] : []`), so there is one cycle algorithm, not two.

Deleting a card cascades inside the same `mutation()` call that removes it — clearing the id from every other card's `blockedBy` and clearing `parentId` on every child — rather than as separate `editCard` calls per affected card (contrast with `deleteMilestone`, which does call `editCard` per unassigned card, because a milestone is not itself a card and so isn't already inside a card mutation). Folding the cascade into the same mutation means one `audit()` pass produces one coherent "delete" activity entry per affected card, and undo restores the whole picture — the deleted card plus every reference to it — as a single step.

Epic child progress counts all children regardless of archived state (`done` is `completedAt !== null`), unlike the WIP column count's explicit non-archived rule: nothing in this release's scope asked for archived children to disappear from a parent's rollup, and archived cards still representing real (if hidden) scope is the same reasoning the planning extension already uses for project totals.

New status colours reuse existing tokens wherever the status already shares a meaning: WIP-at-limit and WIP-over-limit reuse `--due-soon-*`/`--due-overdue-*` (both are "attention" and "exceeded" signals respectively), the waiting-on-a-dependency badge reuses `--due-soon-*`, and the epic chip reuses the neutral `--chip-*` label-chip tokens — so no new hex literals were needed for any of them. `--blocked-text`/`--blocked-bg` is the one genuinely new colour pair this release adds (a card's blocked state is its own kind of status, not a restyled due date), defined in the light `:root` block and in both dark blocks with byte-identical values, and added to `tests/theme-contrast.test.ts`'s checked pairs.

## Milestones

A milestone is a dated outcome a project's cards can optionally belong to; it carries no scheduling authority of its own. `milestoneId` is relationally validated against the card's own project on live cards only. Activity history re-validates it structurally (a nonempty string, via the same `checkCard` every card goes through) but not relationally: a milestone can be deleted while its unassignment is still being written as the current mutation, and that mutation's own "before" activity snapshot necessarily still names the milestone that is simultaneously leaving `project.milestones`. Relationally re-checking history against current `milestones` would make every such delete fail its own validation. This mirrors the existing precedent for `columnId`, labels and assignees, which are also validated structurally in history but never relationally re-checked against live state.

The capacity-per-working-day rate (`focus × availability × FTE × team efficiency`) is factored out of `estimateProject`'s existing sprint-capacity formula (`capacity = 5 × sprintWeeks × that rate`) into `capacityPerWorkingDay`, so the milestone overview reuses the one capacity formula instead of deriving a second one. A milestone's fit verdict compares the cumulative remaining IED range of every milestone on or before its date (sorted ascending) against capacity for the working days from today through that date; the "N unestimated cards" withheld count is likewise cumulative, because an earlier milestone's unsized scope makes every later milestone's capacity comparison unreliable too. "Remaining" only sums cards not currently in a done column; archived cards still count as total scope but not as done unless their column is done, matching the planning extension's "archived counts as scope, deleted doesn't" rule exactly (milestone overview reuses `projectCards`, so there is nothing extra to implement there).

## IED catalog, Custom task and Lab access

The old flat 19-entry `baselines` list stays in `src/planning.ts` unchanged, including `defaultEffort(baselineId)`: it is the only way an old stored estimate (`effort.baseline` set to one of those ids) and an old calibration's frozen `inputs` keep validating and computing the same numbers. It is simply no longer offered as a *choice* for a new estimate — the two-level catalog (`Category` → `Subcategory`) replaces it there. A category is either split (fixed `rtl`/`verification` IED, the design table) or unsplit (an `other` range, the lab and debug tables); `validateCatalog` requires exactly one of the two per category, mirroring how the old `Baseline` type already distinguished split baselines from the `other`-only legacy-debug/timing-closure rows.

Choosing a category and subcategory on a card sets `effort.baseline` to the sentinel `"custom"` and records `category`/`subcategory`/`subcategoryFactor` alongside the filled-in RTL/verification/other values — the provenance lives in those three new optional fields, not by inventing a second meaning for `baseline`. "Custom task" (no category) uses the same `"custom"` sentinel with `category`/`subcategory` left as the literal string `"custom"` too, not `undefined`: the effort form's self-check runs `validate(collect())` once at mount, before any field has been touched, and `collect()` always reads a concrete value out of the rendered `<select>`, so the untouched state and the "touched, chosen custom" state have to be the same string or the very first render of an old card would show a spurious validation error. `effort.category !== "custom"` is therefore the one place (the relational check in `validateWorkspace`) that treats the sentinel specially; every other check (`validateEffort`'s structural check) just requires non-empty text, same as any other reference field.

The RTL/verification/other fields are now always visible and editable regardless of category — removing the old `<details>`-collapsed "Baseline split" section once was simpler than keeping two different layouts for "catalog-filled" and "custom", and it is what the principal asked for Custom task specifically. Editing any of the three fields by hand clears `category`/`subcategory`/`subcategoryFactor` and resets the category control to Custom task, so the stored provenance never claims a catalog number that the user has since overridden.

Lab access (Table 2) is a per-module correction factor like Spec, Clock, Timing or Reuse, not a property of the catalog category — a Board bring-up card and a Hardware testbench card can each be on a dedicated bench or a shared one. It is a plain numeric `factors.lab` field (`?? 1` for old data, matching every other optional factor), not a fourth select-with-discrete-options control; `labAccess` in `src/planning.ts` exists only to give the three named conditions (and their 1 / 1.25 / 1.5 values) a single source that the catalog-label-sync test and the UI guidance text both read from, so the doc, the code and the on-screen hint cannot drift apart silently.

Workspace catalog edits (`addCategory`/`editCategory`/`deleteCategory`/`addSubcategory`/`editSubcategory`/`deleteSubcategory`) write to `Workspace.catalog`, which starts absent (meaning "use the built-in `defaultCatalog`") and is cloned into existence on the first edit — the built-in array itself is never mutated, so a workspace that never touches the catalog editor keeps loading byte-for-byte. Deleting a category or subcategory still referenced by a live card throws rather than silently unassigning it, unlike milestone deletion: a milestone is a schedule label a card can simply lose, but a catalog reference is also carrying a computed factor into the card's stored IED numbers, so losing the reference without the user re-deciding the number would be a silent effort-estimate change.

## Boards, My work, templates and bulk actions

`Board` and `Column` already supported several boards per project; only `currentBoard()` picking the first board was missing a real selector. The active board is now a `Filters.board` field, round-tripped through the URL fragment exactly like `project` — `encodeFilters`/`decodeFilters` already iterate `Object.keys(emptyFilters)` generically, so adding the field needed no change to either function. `render()` normalizes an invalid or missing `filters.board` to the project's first board the same way it already normalized `filters.project`, so an old bookmarked fragment with no `board` key, or one naming a board that was since deleted, still resolves to something real instead of showing an empty board.

`addBoard` factors the five-column default set out of `createProject`, which now just creates the project record and calls `addBoard` — one board-creation path, not two that could drift. Cross-board card moves stay forbidden through `moveCard` (its existing `source.boardId !== target.boardId` check is untouched); a new `moveCardToBoard` is the one explicit path that crosses boards, used by `deleteBoard`'s cards-to-destination step and by the card detail's "Move to board…" control. It still refuses a destination outside the card's own project, matching `moveCard`'s same-board-family spirit and the same-project rule `blockedBy`/`parentId` already enforce — without that check, a card could carry a blocker or parent reference into a project it no longer shares with that reference, failing validation later with a confusing error instead of a clear one at the point of the move. `deleteBoard` refuses to remove a project's last board (mirroring `deleteColumn`'s "keep at least one column"), and like `deleteColumn` it requires an explicit destination only when the board actually holds cards — an empty board deletes immediately. Both the column-level and board-level deletion cascades now share the same shape: find affected cards, require a destination if there are any, move each one through the mutation path (so Activity, undo and `completedAt` all follow), then remove the empty container.

My Work is a pure function (`myWork(workspace, memberId, at)`) with an injectable clock, the same pattern `dueState` and `matches` already use for testability, kept in its own module rather than inside `model.ts` because it computes a cross-cutting view rather than mutating or validating domain state. Done cards are placed in a collapsed "Done" group rather than excluded: excluding them would make a just-finished card vanish from the one place that shows "what's assigned to me," which reads as data loss even though nothing was deleted. Opening a card from My Work that belongs to another project or board switches `filters.project`/`filters.board` to that card's real location before calling the existing `openCard` — the alternative (rendering card detail without changing the active board) would leave the "Blocked by"/"Epic parent" dropdowns scoped to whatever board happened to be active, which was already a board-scoped simplification before this release and is not something this feature should make worse.

Card templates store label *names*, not label IDs, in `CardTemplate.labelNames` — templates are workspace-level data, but labels are project-scoped, so an ID saved from one project's card could not be resolved (or could resolve to the wrong label) when the template is used in another project. `createCardFromTemplate` resolves names to IDs by matching an existing project label case-insensitively and creating a new one if none matches, reusing exactly the lookup `app.ts` already uses when a user types label names by hand in the card detail view. Creating a card from a template is one `mutation()` call (one Activity entry, one undo step), not `createCard` followed by a patch, so a template-created card's history reads as a single "create" rather than a "create" immediately followed by an unrelated-looking "edit". Board templates capture only `name`, `wipLimit` and `done` per column — enough to reproduce the *shape* of a flow, not card content or per-column card counts, which would make "board template" ambiguous with "duplicate board".

Multi-select is ephemeral UI state (`const selected = new Set<string>()` in `app.ts`), never written into the workspace or validated: a selection has no meaning once persisted, and keeping it out of `Workspace` keeps the schema-2 byte-for-byte guarantee from having to account for it. Each bulk action calls the normal per-card model function (`editCard`, `moveCard`, `archiveCard`) in a loop inside one `stage()` call; no bulk-specific mutation function was needed because `Session.change` already treats one `stage()` call as one undo step regardless of how many model functions run inside it, while each individual model call still produces its own `audit()` entry — so "one undo step, one Activity entry per affected card" was already the existing architecture's behavior for free, not a new mechanism built for this feature. Selection is cleared on project/board switch and on Escape, but deliberately not by board-level re-renders triggered elsewhere (e.g. search-as-you-type), so filtering the board does not silently drop a selection the user is still building.

## Sprint capacity: derived, direct and per-sprint overrides

`Planning.capacityMode` ("derived" | "direct", default "derived" when absent) only changes what `capacityPerWorkingDay` returns: in direct mode it is `directCapacity / (5 × sprintWeeks)`, reusing the same per-working-day shape the derived formula already produces, so every existing consumer of that one function — `estimateProject`'s sprint capacity, `sprintLoads`, the new `sprintBoard`, and `summarizeMilestones` (via `capacityPerWorkingDay` directly) — picks up direct mode for free. The calendar quote (`weeks`, `sprints`, coarse `bandWeeks`) divides by the same effective weekly capacity, so in direct mode weeks and sprints always agree with the entered IED per sprint. Effort-equivalent `workingDays` is omitted in direct mode: it needs focus × availability, which one IED-per-sprint figure does not separate out.

Per-sprint overrides (`Planning.sprintOverrides`, sprint number as a string key to a capacity) exist only to answer "what if this particular sprint is short" (a holiday week, a booked-lab week) without touching the project's baseline capacity mode. They apply in exactly one place — `sprintBoard`, which backs the Sprints view — and nowhere else, because sprints carry no dates anywhere in this app: the milestone overview and the project summary's calendar/weeks/sprints-count numbers all assume every sprint has the project's one capacity. Overriding sprint 3 does not and cannot make the milestone overview know sprint 3 is short, since the overview has no notion of "sprint 3" to begin with. `setSprintOverride` refuses to write until `project.planning` exists, matching the existing gate on every other planning write (the Sprints view's capacity/clear controls simply surface whatever error that throws through the normal storage-status banner, the same path `deleteCategory`'s refusal uses).

## Calendar and timeline views

The view switcher (`data-view="board"|"calendar"|"timeline"` buttons in the viewbar) is the minimal set this slice owns; a parallel slice adds its own `data-view="list"` button the same way, and the two are expected to merge side by side rather than one replacing the other. `Filters.view` is a plain additive string field (`""` meaning Board), round-tripped through the URL fragment exactly like every other filter via the existing generic `encodeFilters`/`decodeFilters`, so no schema or migration work was needed. `render()` now shows only the active view's section and calls only that view's render function — `renderBoard()` never runs while Calendar or Timeline is active — and every call site that used to trigger a board-only re-render (search, the filter dropdowns, a card-detail edit closing behind the dialog) now calls a small `renderActiveView()` dispatcher instead, so filters and in-place edits stay live across all three views, not just the board.

Both new views are pure-function-plus-mount modules (`src/calendar-view.ts`, `src/timeline-view.ts`), matching the shape `src/milestones.ts`/`src/milestones-ui.ts` and `src/my-work.ts`/`src/my-work-ui.ts` already established: a pure data/layout function the unit tests exercise directly, and a thin DOM-mounting function with its own small module-level UI state (current month/week anchor, expanded days, timeline group-by) — the same pattern `app.ts` itself already uses for ephemeral UI state (`selected`, `dragging`) that has no business being persisted workspace data.

**Calendar** never computes a "today" internally beyond an injectable default, so `monthGrid`/`weekGrid`/`cardsByDay`/`milestonesByDay` are deterministic and unit-tested on fixed dates (month boundaries, both a leap and a non-leap February, Monday-first week starts regardless of where the 1st falls). The only date write in the whole view is the drag-and-drop handler calling `editCard(w, cardId, { dueDate })` — the same mutation path every other due-date edit already uses, so it is one Activity entry and undoable, and dropping a dated card back onto the "No due date" list clears it through the identical call with `dueDate: null`. A day's "+N more" expansion and the current month/week anchor are kept as in-module UI state, not written to the workspace or the URL, matching how card selection and drag state are already handled in `app.ts`.

**Timeline** adds one new optional, additive schema-2 card field, `startDate?: string`, validated the same way `dueDate` already is (`isoDate`) plus one relational rule — a start date must not fall after the due date — checked inside `checkCard` itself rather than in `validateWorkspace`'s cross-card relational pass, because the rule only ever compares two fields on the same card, exactly like the priority/estimate checks already living there. `layoutTimeline` only draws a bar for a card with both dates; a card with only one, or neither, goes to `notScheduled` rather than the view inventing the missing half. The scheduled day range always spans at least the current week and always includes today (extending backward or forward as needed) so the today-line is never computed outside its own chart's range. Grouping by epic puts a parent card's own bar in its children's group — labelled by the epic's title — rather than leaving it in "No epic", since a Gantt-style epic row reads naturally as the epic followed by its children, not as two disconnected places to look. A dependency arrow is only drawn when both the blocker and the dependent have a bar (i.e. both are fully scheduled); an unscheduled blocker reference is surfaced by the blocked card's own "Not scheduled" listing, not by a dangling arrow. The pure layout function returns day-unit offsets and spans (`data-start-offset`/`data-span` on each rendered bar), so the mount function's day-to-pixel conversion is the only place that knows about pixels, and the browser test asserts geometry through those data attributes rather than parsed computed styles.

Every colour the two views use — day-cell drag highlight, milestone markers, conflict arrows — reuses an existing theme token (`--drag-over`, `--due-soon-*`, `--planning-warning-text`) chosen for a meaning that already matches, the same reuse discipline the flow-control and milestone work already established; neither view needed a new CSS custom property or touched `tests/theme-contrast.test.ts`.

**Timeline legibility pass (review follow-up).** `dayPx(root, days)` replaces the fixed 28px day width: it reads `root.clientWidth` (the mounted section, which is already unhidden by the time `render()` calls `mountTimeline`) and fills the panel so a short range isn't a sliver of tiny bars, clamped to a 24px floor so a long range still gets a usable minimum width and scrolls horizontally past it — `.timeline-scroll`'s existing `overflow-x:auto` needed no change. `axisTicks` is a separate pure function (unit-tested on fixed fixtures, same as `layoutTimeline`) rather than folded into it: it only needs `rangeStart`/`days` and an optional locale, so keeping it pure and separate from the card-grouping layout means it is swappable or reusable (the calendar view's own month/week header) without carrying grouping concerns. Every week boundary always gets a full `Intl`-formatted label (weekday, day, month); the day ticks between boundaries thin out as the range grows (every day up to 31 days, every 2nd up to 60, every 7th beyond) so a long project doesn't crowd the axis into overlapping text — the thinning never drops a week boundary itself, since that check runs first.

Two separate bugs were behind the "Rush" label sitting under an arrowhead: the SVG arrow layer was the last thing written into `innerHTML`, so it painted over the bars with no z-index to say otherwise; and the arrow's Y endpoint used the row's full slot height (`ROW_PX`, 30px) over two, not the bar's own rendered height (`BAR_PX`, 20px) over two, landing a few pixels off the bar's true vertical centre. Both are fixed together — arrows now render first in markup and carry a lower `z-index` than bars, group labels and the axis, and `fromY`/`toY` use `BAR_PX / 2` — rather than papering over the symptom with one fix alone. A bar's visible text keeps its existing truncation (`overflow:hidden;white-space:nowrap`, now also `text-overflow:ellipsis`) and gained a `title` attribute carrying the untruncated name, matching how `blockedBadge`/`waitingBadge` already use native tooltips for truncated or iconised status text elsewhere in `app.ts`.

## Milestone burnup

`milestoneBurnup(w, milestoneId, today)` (`src/burnup.ts`) derives a daily scope/done series entirely from the existing Activity log — there is no new history store or card field. A card's state at any instant is the `after` of its latest Activity entry at or before that instant, or that entry's `before` beforehand; a card with no Activity entries at all falls back to its current fields, appearing at `createdAt` and completing (if ever) at `completedAt`. This is built as a sorted sweep over per-card scope/done change points, not a days × cards × activities scan: each card contributes a short list of instants where its (in scope, done) pair actually changes, those lists merge into one sorted event stream, and the daily series is read off that stream alongside the day boundaries in a single pass.

Scope counts archived cards (matching the planning extension's "archived counts as scope" rule, and `summarizeMilestones`' existing behaviour) and drops a card the moment its own history shows it deleted (`after: null`) or unassigned from the milestone; "done" is `completedAt !== null` at that same instant, which by the workspace's own invariant means "in a done column" at that time, including when a column's own done flag is toggled rather than the card being moved. Undo needs no special case: it already appends ordinary Activity entries (see "Activity and undo" above), so a reverted completion shows up as a normal state change at the undo's timestamp, leaving every earlier day's reading untouched. The series starts on the first day any card's history shows it carrying the milestone, through today; a milestone nobody has ever carried returns an empty series rather than a zero-filled one.

The series' last point is required to equal `summarizeMilestones`' `doneCards`/`totalCards` for the same milestone, and does so by construction: a live card's current fields are always exactly its latest Activity entry's `after` (or its own fields, for a card with no history), so replaying history up to now and reading today's live state are the same computation reached two different ways.

There is no projected, ideal or forecast line and no completion date is stated anywhere in the chart, matching this app's planning views being lenses rather than a delivery schedule (see "Milestones" above): the drawn line simply stops at today, even when the milestone date is still ahead. When the milestone date is in the future, the chart's date axis extends out to it so the date marker has somewhere to sit; a milestone date already in the past keeps the axis at today, since extending further wouldn't show anything. Sprint burnup is out of scope for the same reason sprint overrides already stop at `sprintBoard` (see "Sprint capacity" above): sprints carry no dates anywhere in this app, so there is no axis to draw one against.

The chart (`src/milestones-ui.ts`) reuses existing theme tokens rather than adding any: the done line and today marker use `--accent` (the same token `.milestone-verdict` and the progress bar's fill already use for "on track"/"complete"), the scope line uses `--muted` (dashed, so the two lines read apart by shape as well as colour), and the milestone-date marker uses `--due-soon-text` — the same colour the card's milestone chip already carries, so "this line is about the milestone" reads as the same signal in both places. Axis labels, legend text and the screen-reader summary (`<title>`, `aria-label` and a `.visually-hidden` paragraph stating scope/done/remaining as plain numbers) use `--text`/`--muted` like the rest of the dialog. No new token was needed, so `tests/theme-contrast.test.ts` did not need a new pair.

Chart geometry is computed in day-unit offsets and percentages, never raw pixels, so it fits any container width (the 720px milestones dialog down to a 390px phone) with plain CSS percentage positioning instead of a `clientWidth` measurement — unlike the timeline view, the burnup chart never needs horizontal scroll, since nothing inside it needs a minimum per-day pixel width to stay legible. Because of that, its date-axis ticks use a dedicated `burnupAxisTicks` (capped to a fixed tick count) rather than the timeline view's `axisTicks`: that function thins by day count for a *scrolling* chart with a fixed day width, and produced overlapping labels on a 30-day range squeezed into a non-scrolling 390px chart. A single-point series (a milestone assigned to a card for the first time today) would otherwise draw a zero-length path; a short half-day stub keeps that day's value visible as a flat dash without implying anything about tomorrow.

## Keyboard navigation, command palette and quick-add

A quick-added card's label, assignee, priority, due date and milestone all land through one `createCard(w, columnId, title, at, patch)` call rather than a `createCard` followed by `editCard` calls: `createCard`'s existing `mutation()` wrapper only fires once, so the whole card — however many tokens it parsed — produces exactly one Activity entry and one undo step, matching what typing a plain title already does. `patch` defaults to `{}`, so every existing call site is unchanged. Label resolution (`resolveLabels`, lifted out of the card-detail label field's existing inline logic so quick-add reuses it instead of duplicating it) still runs first and pushes onto `project.labels` inside the same `stage()` callback, before `createCard` runs — that write isn't itself audited (`mutation()` only diffs `w.cards`), so it rides inside the one card-creation entry for free, and undoing that entry restores the whole project snapshot, label included.

`parseQuickAdd` (`src/quickadd.ts`) takes an injectable `today` (default `new Date()`) purely so its weekday/`today`/`tomorrow` math is deterministic in tests; the app never passes one. Assignee and milestone matching share one `uniquePrefix` rule — a case-insensitive prefix of the *whole* name, resolved only when exactly one candidate matches — rather than two different rules: because a person's name is typically "First Last", a whole-name prefix already *is* a first-name prefix in the common case, without a second code path for "first word only". An unresolved or ambiguous token (unknown member, bad priority word, invalid or ambiguous date/milestone) is simply never stripped from the title — the parser has no error path, only "consumed" or "left alone".

`j`/`k` walk a single flattened list — every visible column in position order, each column's visible cards in position order (`visualOrder` in `src/keyboard.ts`) — rather than hopping within a column first: that flattened order is the same left-to-right, top-to-bottom order the board already renders in, so it needs no separate "visual" concept to keep in sync with the DOM. Both `j`/`k` and `←`/`→` clamp at either end instead of wrapping, and `n`/arrow-key moves use the DOM's native focus (no new "focused" CSS class) so the existing `button:focus-visible` outline is the only focus indicator — a card that is keyed back into the same DOM node after a re-render (see `renderBoard`'s existing reuse map) keeps that native focus automatically.

Ctrl+K opens the command palette even while typing in a field, unlike every single-letter shortcut, which is ignored under the same typing/dialog guard as `/`: a modifier chord is vanishingly unlikely to collide with real typing, and every command-palette precedent (editors, issue trackers) keeps that binding live everywhere. The palette itself is a thin DOM wrapper (`mountPalette`) around two pure functions, `fuzzyScore` and `rankItems`, so the ranking rule (prefix, then word-start, then subsequence, each tier breaking ties alphabetically) is unit-testable without a browser.

## Swimlanes and the list view

`Board.swimlane` grew from the hardcoded `"none"` literal to `"none" | "assignee" | "priority" | "label" | "epic"` (`swimlaneKinds` in `src/model.ts`) — the field already existed and was already validated, so this is a pure widening of an existing additive field, not a new one; an old workspace's boards already carry `swimlane: "none"` and keep loading unchanged. `"none"` doubles as the sentinel for every kind's None lane (a card with no assignees/labels/parent, or literally no-priority) — safe to share because priority's own `"none"` value already means the same thing there, and `assignee`/`label`/`epic` have no real id that collides with the string `"none"`.

Lane membership (`src/swimlanes.ts`, pure and unit-tested) is multi-valued for `assignee` and `label` — a card with two assignees appears in both lanes — and single-valued for `priority` and `epic`. `moveCardInLane` (`src/model.ts`) reflects that split: an assignee/label move removes the *source* lane's membership and adds the *target* lane's (so dragging a two-assignee card out of one lane only drops that one membership, per the brief), while a priority/epic move just sets the new value outright, since there is only ever one. The column/position change and the attribute change happen inside one `mutation()` call, exactly like every other card mutation, so Activity and undo already work for free — no bespoke undo handling was needed. An epic-lane move that would create a parent cycle or cross projects is rejected by the existing `validateWorkspace` checks that `parentId` edits already go through (`checkNoCycle`, same-project), via the same clone-validate-discard path `Session.change` already uses for every mutation — `moveCardInLane` itself does no epic-specific validation, it only has to produce a workspace that the existing relational checks accept or reject.

The swimlane board is one flat CSS grid (`src/app.ts`'s `renderSwimlaneBoard`, `.swimlane-grid` in `src/styles.css`), not one grid per lane row as the first version had it: nested per-row `auto-fit` grids each pick their own wrap point once the board is wider than the viewport, and at five-plus columns they drifted out of alignment with each other and with the header. A single grid with a fixed `repeat(columns.length, …)` column count, and every lane's label-plus-cells as flat children of that one grid, keeps every row's cells in the same columns by construction — there is no per-row layout decision left to diverge. The swimlane board intentionally skips the keyed-DOM-diffing `renderBoard` (now `renderPlainBoard`) uses for the 1,000-card move test: it is a full `innerHTML` replace on every render, acceptable because swimlanes are opt-in and the performance budget's own card-count scenario runs with the default `"none"` swimlane, which still takes the untouched `renderPlainBoard` path.

The list view (`src/list-view.ts`) keeps sorting and grouping as two independent, composable pure functions (`sortRows`, `groupRows`) rather than one combined "sorted-and-grouped" function: `sortRows` always governs the order of rows *within* a group, but a group's own position is fixed by field (board column order for `column`, priority rank for `priority`, else alphabetical with the None/Unassigned bucket last) and deliberately does not flip with the sort direction — grouping by priority and clicking the header to sort descending still shows the groups none→urgent, just as ascending would, because re-ordering the groups themselves on every sort click would make a stable layout reshuffle for a control (direction) that only makes sense within a group. `sortRows` tags each row with its original index before sorting and falls back to it on a tie, which is what makes the sort stable regardless of the JS engine's own `Array.sort` stability guarantees. Both `view` and the list view's `sort`/`group` are plain `Filters` fields defaulting to `""` (board / title-ascending / ungrouped) so they fall out of `encodeFilters`/`decodeFilters`'s existing generic `Object.keys(emptyFilters)` loop for free, the same way `board` did in the boards release.

`render()`'s per-view dispatch is centralized in one `renderActiveView()` function, called both by `render()` itself and by every filter control's own handler (search, the seven `#filter-*` selects) in place of the `renderBoard()` they used to call directly — without that change, typing in search while the list view was open would silently update the hidden board underneath it and leave the visible table stale.

## Card aging

`Column.agingDays` is an optional, additive schema-2 field (`number | null`, absent on every column until a user sets or clears it in the column settings dialog) validated with the exact same positivity rule `checkedWipLimit` already applies to `wipLimit` — a stored or written threshold must be a positive whole number, never zero, negative or fractional. `createBoardFromTemplate`/`saveBoardTemplate` capture and reproduce it on `BoardTemplateColumn.agingDays` the same way they already do for `wipLimit`, so a saved flow keeps its aging configuration. An old or untouched column simply never gains the key, so existing workspaces load byte-for-byte unchanged.

A card's age is derived entirely from Activity, not stored on the card itself: `src/aging.ts`'s `columnEntryIndex`/`cardAgeDays` walk the latest Activity entry for a card whose `after` names the column it currently sits in, and whose `before` is either absent or names a different column — the moment it actually entered where it now is. An edit that leaves the column unchanged produces an Activity entry too, but that entry's before/after columns agree, so it is never mistaken for a fresh entry and the age does not reset. A card with no such entry (crafted or imported history, or history older than the app has kept) falls back to `card.createdAt`.

Undoing a move counts as entering the column: `undoWorkspace`'s own audit entry has `before` naming the column the card was in just before the undo and `after` naming the column the undo restored it to. When those differ, the undo entry itself satisfies the "entered this column" rule and becomes the new age baseline — intentional, since from the card's perspective the undo really did just place it there, the same way a manual move would have.

Done columns never show an age badge regardless of threshold: a card that has reached a done column is finished, and flagging it as stale would contradict the column's own meaning. The badge is amber from the threshold and red from twice the threshold, reusing `--due-soon-*`/`--due-overdue-*` exactly as the WIP-limit badge already does (see "Flow control" above), so no new colour token was needed and `tests/theme-contrast.test.ts` needed no change.

Rendering never scans `w.activities` or `w.cards` per card. `src/app.ts` keeps a `WeakMap`-cached column-entry index (cardId → latest qualifying Activity timestamp), built once per `activities` array identity and extended only over the entries appended since the last render — mirroring the existing `cardIndex()` cache and its "activities are append-only, a restore replaces the array" assumption exactly. `cardHTML` takes its column as a parameter supplied by the loop that already has it (`renderPlainBoard`'s and `renderSwimlaneBoard`'s own `columns.map(col => ...)`), rather than looking it up with a scan of its own.
